# 04. Backend Architecture

**Project:** CineNest

**Version:** 1.0

**Status:** Planning Phase

---

# 1. Purpose

This document defines the backend architecture of CineNest.

The backend is responsible for managing user-specific data, authentication, authorization, business rules, and secure communication between the frontend and persistent storage.

Unlike traditional streaming platforms, CineNest does not host movie metadata or video files. Instead, the backend focuses exclusively on application data generated by users.

---

# 2. Why Appwrite?

Appwrite has been selected because it provides a complete Backend-as-a-Service (BaaS) platform that integrates well with React applications while reducing infrastructure complexity.

Appwrite provides:

* Authentication
* Database
* Storage
* Realtime
* Functions
* Permissions
* Session Management

This allows CineNest to focus on application features rather than backend infrastructure.

# 5. Backend Modules

The backend will be organized into logical modules.

```text
backend/

appwrite.js

auth/

database/

storage/

functions/

permissions/

repositories/

validators/
```

---

## appwrite.js

Responsible for:

* Initializing the Appwrite SDK
* Exporting configured clients
* Centralizing backend configuration

---

## auth/

Responsible for:

* Registration
* Login
* Logout
* Email verification
* Password reset
* Session validation

---

## database/

Responsible for:

* CRUD operations
* Collection access
* Query helpers

The UI should never communicate directly with collections.

---

## storage/

Responsible for:

* Avatar uploads
* Future image uploads
* File management

---

## functions/

Responsible for backend automation.

Examples:

* Update watch history
* Generate notifications
* Analytics aggregation
* Cleanup tasks

---

## permissions/

Responsible for defining access rules.

Examples:

* User permissions
* Admin permissions
* Read permissions
* Write permissions

---

## repositories/

Repository modules abstract database operations.

Example:

Instead of:

```javascript
databases.createDocument(...)
```

throughout the application,

the UI will call:

```javascript
favoriteRepository.add(movie)
```

The repository handles Appwrite-specific implementation details.

This improves maintainability.

---

## validators/

Responsible for validating data before saving.

Examples:

* Comment length
* Rating value
* Username validation
* Required fields

---

# 6. Backend Communication

The frontend communicates with Appwrite through dedicated backend modules.

```text
React Component

↓

Hook

↓

Repository

↓

Database Module

↓

Appwrite SDK

↓

Appwrite Services
```

This architecture prevents UI components from depending directly on Appwrite.

---

# 7. Authentication Flow

```text
User

↓

React Form

↓

Auth Module

↓

Appwrite Authentication

↓

Session Created

↓

React Updates UI
```

Authentication logic should remain isolated from UI components.

---

# 8. Database Flow

```text
User Action

↓

Repository

↓

Database Module

↓

Appwrite Database

↓

Response

↓

React UI
```

The frontend should never manipulate Appwrite documents directly.

---

# 9. Security Strategy

The backend must enforce:

* Authentication
* Authorization
* Collection permissions
* Document permissions
* Input validation
* Secure sessions

Security should never rely solely on frontend checks.

---

# 10. Session Management

Appwrite sessions provide:

* Persistent login
* Multiple devices
* Session expiration
* Device information
* Secure logout

The frontend should restore user state from the active session during application startup.

---

# 11. Realtime Strategy

Appwrite Realtime may be used for:

* Notifications
* Live admin updates
* Watchlist synchronization
* Comment updates

Realtime should only be introduced where it improves the user experience.

---

# 12. Storage Strategy

Appwrite Storage will initially be used for:

* User avatars

Future possibilities include:

* Custom banners
* Promotional images
* Admin uploads

Movie posters and backdrops will continue to come from TMDB.

---

# 13. Error Handling

The backend should provide meaningful error responses.

Examples:

* Invalid credentials
* Email already exists
* Permission denied
* Collection unavailable
* Network timeout
* Session expired

The frontend should translate technical errors into user-friendly messages.

---

# 14. Logging Strategy

Important events should be recorded.

Examples:

* Login
* Logout
* Movie request
* Report submission
* Review creation
* Account creation

This data can later support analytics and auditing.

---

# 15. Scalability

The architecture should allow future migration to a custom backend.

Possible migration:

React

↓

Node.js API

↓

PostgreSQL

↓

Redis

↓

Object Storage

without requiring major frontend changes.

---

# 16. Engineering Decisions

## ADR-009

Appwrite is the single source of truth for user data.

Reason:

Centralized user management simplifies authentication and synchronization.

---

## ADR-010

Movie metadata remains outside Appwrite.

Reason:

Avoids duplicated storage and synchronization issues.

---

## ADR-011

Database access is abstracted through repositories.

Reason:

Keeps UI independent of backend implementation.

---

## ADR-012

Business logic should remain outside React components.

Reason:

Improves maintainability and testing.
